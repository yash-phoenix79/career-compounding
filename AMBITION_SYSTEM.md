# Ambition System: AI-Native Engineer, Builder, and Founder

## North star
Become an AI-native product and systems engineer who can turn ambiguous, real problems into reliable, useful software; grow into high-impact technical leadership; build public trust through evidence; and eventually create a business when real customer demand is demonstrated.

This is a direction, not a promise or a reason to start multiple parallel tracks.

## Priority hierarchy
1. **Primary engine:** engineering capability and reliable delivery at Amazon.
2. **Daily craft:** backend fundamentals, LLD, AI engineering.
3. **Compounding assets:** one active project, open-source contributions, public proof of work, technical relationships.
4. **Future option:** validate and build a business around a demonstrated user problem.
5. **Foundation:** sleep, health, attention, and sustainable execution.

## Locked operating contract
- Every day: Backend from First Principles, LLD, AI knowledge.
- Every weekend: one tangible contribution to the existing active project.
- Target 60 minutes daily; maximum 90 planned learning minutes.
- On difficult days, shrink the session; do not create guilt debt or all-nighters.
- Protect Amazon delivery and sleep.
- Keep one main project active. Do not start a new project to escape a hard task.
- Record evidence in `PROGRESS.md`; passive consumption is not completion.
- Freeze the system for 30 days. Change it only in response to an observed failure.

## Agency and reality modeling
For meaningful decisions, distinguish:
1. Observation: what actually happened?
2. Interpretation: what might explain it?
3. Hypothesis: what do I predict?
4. Cheapest useful test: how can I test this?
5. Update: what did the evidence change?

Practise agency by closing meaningful loops, validating assumptions, asking for help early, communicating blockers and risks, and owning outcomes end to end. Track problems resolved and outcomes improved—not hours of activity or how independently you struggled.

Seek disconfirming evidence. Separate outputs (code, posts, study hours) from outcomes (reliable features, users helped, incidents prevented, customers retained). When wrong, update without ego.

## Healthy attention and motivation
- Work in a single focused block; start at 20 minutes and extend gradually when sustainable.
- Put the phone and unrelated tabs away. Capture distracting ideas to review later.
- Reward competence, completion, autonomy, and useful feedback—not streak anxiety, guilt, or novelty.
- Finish sessions by recording what changed in understanding, what was completed, and the next action.
- A tiny recovery session is acceptable on hard days; sleep takes priority when exhausted.
- Create before consuming. Social feeds and tool research happen only after meaningful work, within a bounded window.

## AI-native engineering
Use the loop: **Specify → Orient → Plan when ambiguous → Delegate a bounded task → Inspect the diff → Test → Understand → Ship.**
The human remains accountable for requirements, architecture, security, verification, and outcomes. Do not treat generated code as understood code.

Learn capabilities when a real task calls for them: model APIs, structured outputs, tool calling, state, retrieval when justified, evaluations, prompt-injection defenses, permissions, tracing, latency, and cost. Start with one coding agent and a boring, effective stack. Add frameworks, databases, orchestration, or agents only when evidence shows they solve a current problem.

For AI features, maintain representative evaluations, critical failure checks, regression tests, and visibility into quality, latency, and cost.

## Engineering quality and launch
Use `ENGINEERING_PROJECT_CHECKLIST.md` as a risk-based map, not a demand for enterprise complexity. Launch the smallest useful vertical slice with clear users/problem, tests for critical behavior, appropriate security/privacy, reproducible setup, deployment/recovery basics, error visibility, useful docs, and user feedback. Defer microservices, Kubernetes, Kafka, vector databases, and multi-agent orchestration unless justified by real needs and scale.

## Open source and packages
- Choose one relevant project/ecosystem and use it before trying to contribute.
- Learn its setup, conventions, tests, issues, and contribution process.
- Start with a reproducible bug, test, documentation improvement, or small focused fix.
- Optimize for useful, reviewed contributions and learning—not raw PR counts.
- Create a package only after solving a recurring problem. A good package has a clear purpose, good API, sensible defaults, predictable errors, tests, documentation, safe behavior, versioning, and evidence of real use.
- Do not invent packages to fill a portfolio.

## Public presence and community
Positioning: an engineer documenting real progress from backend fundamentals to AI-native systems and useful products.
- Publish up to two substantive posts per week based on actual experiments, shipped work, or lessons.
- Engage thoughtfully with relevant engineers in bounded sessions.
- Share demos or project updates when there is real progress.
- Be honest about what is known, tested, and still uncertain. Never disclose confidential employer information.
- Measure useful conversations, feedback, relationships, and people trying the work; follower count is secondary.
- Study at most one role model per week, only when relevant to a current problem, and apply one practice.

## Business with an AI crew
Start with a painful, recurring problem for a specific user—not a multi-agent architecture.
1. Talk to users and observe current workarounds.
2. Test assumptions cheaply; disprove weak ideas early.
3. Deliver the smallest useful solution, manually or with simple software if appropriate.
4. Measure activation, repeat usage, user outcomes, willingness to pay, acquisition, support burden, and unit economics.
5. Add AI agents only where they improve measurable quality or throughput.
6. Give agents bounded roles and least-privilege access; require tests, logs, human approval for consequential actions, and safe stopping behavior.
7. Expand investment only when evidence supports demand and sustainable economics.

## Ambition and career progression
- SDE-2: independently deliver scoped work, design components, test/debug, communicate early, and own outcomes.
- SDE-3: solve ambiguous cross-component problems, make architecture trade-offs, improve reliability/performance, and lead execution.
- Principal: sustained, organization-wide technical direction, leverage, simplification, and impact on other engineers and business/customer outcomes.
- Product/business outcomes are not automatic consequences of technical skill; validate them separately.
- Make commitments privately, progress visible, and let results earn bigger claims.

## 90-day scorecard
Review weekly, without redesigning the system:
- Work: one meaningful delivery/ownership improvement or lesson, without exposing confidential details.
- Craft: honest evidence for backend, LLD, and AI practice.
- Project: one tangible weekly contribution with a test, demo, design decision, or commit.
- Reality: one assumption tested or corrected.
- Community: useful public artifact or technical interaction when there is genuine evidence to share.
- Health: sleep and recovery protected; no all-nighters to compensate for missed work.

## Decision rule
When choosing what to do next, prefer the action that:
1. Advances the current highest-priority outcome;
2. Produces observable evidence;
3. Teaches a reusable skill;
4. Can be completed within sustainable time;
5. Reduces uncertainty or creates useful feedback.

If an activity fails these tests and is mainly novelty, status-seeking, or planning, defer it.
